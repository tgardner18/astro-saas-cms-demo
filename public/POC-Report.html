Use Case 01

Global Settings Management

Apply global values that can be overridden at the instance level as required. This implementation uses a Global Settings content type to manage pre-determined filters for Category, Topic, and Subtopic parameters across the site, with the ability to override at the page level.

Sample Approach

SOLUTION DETAILS

Create a dedicated Global Settings content type with structured fields to store default filter parameters and configuration values. This approach treats the CMS as a structured source of truth consumed by the frontend via GraphQL.

Define Global Settings Content Type

Create a Block content type named "GlobalSettings" with structured fields for BankingCategoryParam, TopicParam, SubtopicParam, and any other global configuration values.

Create Shared Block Instance

Instantiate a single shared block at the application level in your content tree, accessible to all pages.

Add Page-Level Override Capability

Include optional properties on individual page types to allow authors to override specific global settings when needed.

Implement Frontend Resolution

On the Next.js frontend, fetch both global settings and page-specific overrides. Apply page-level values when present, falling back to global defaults.

💡Additional Considerations

  • Environment-Specific Settings: Consider supporting environment-specific overrides (sandbox vs. production) by using a site key or URL field in the Global Settings content type.
  • Caching Strategy: Global settings should be cached at the edge or in your Next.js build process since they rarely change. Implement cache invalidation when settings are updated in the CMS.
  • Validation: Implement validation to ensure that page-level overrides maintain data integrity and don't conflict with global configurations.
  • Multisite Support: If implementing a multisite architecture, include a site identifier field to support different global settings per site.
  • Query String vs. Content: Evaluate whether these filter parameters need to be content-authorable or if they can be hardcoded. If they're static values used primarily for URL construction, consider making them part of the codebase rather than CMS content.
Use Case 02

Content Item References

Enable authors to create controls (dropdowns, multi-select) that reference content items within the CMS for tagging, categorization, and component relationships.

Sample Approach

SOLUTION DETAILS

Use a hybrid approach leveraging both Choice fields and Content Reference fields depending on the use case:

For Simple Tagging and Categorization

Use Optimizely's Choice field type for flat taxonomy like categories, topics, and tags. Choice fields provide key/value pairs that can be rendered as dropdowns or multi-select controls in the authoring UI.

For Component Relationships

Use Content Reference fields (single or multiple) to reference other content items when building visual components (e.g., Carousel component referencing CarouselSlide items, or a Featured Articles component referencing Article pages).

Configure Search Facets

When using Choice fields for tagging, ensure these fields are indexed in Optimizely Graph to support faceted search and filtering on the frontend.

💡Additional Considerations

  • Hierarchical Taxonomies: Choice fields are flat key/value pairs and don't support Topic/Subtopic hierarchies. If you need hierarchical relationships, consider modeling Topics and Subtopics as separate content types with parent-child relationships.
  • Dynamic Filtering: Current Optimizely SaaS CMS limitations prevent creating truly dynamic "cascading" dropdowns in the authoring UI (e.g., selecting a Topic automatically filters available Subtopics). This would require custom authoring UI extensions, which are not currently supported.
  • Content vs. Configuration: Evaluate whether referenced items are true content that changes frequently or configuration data. For configuration-like references, Choice fields may be more appropriate than full content references.
  • Performance: When using Content Reference fields with many references, consider the GraphQL query depth and implement pagination or limiting to avoid performance issues.
  • Search Integration: Ensure Choice field values are properly indexed in Optimizely Graph to enable filtering and faceted search on the frontend.

Content Authorable Redirects

Provide the ability for content authors to fully manage collections of redirects within the CMS, including source URLs, destination URLs, and redirect types (301, 302).

Sample Approach

SOLUTION DETAILS

Create a structured Redirect content type in the CMS and implement redirect handling at the frontend/edge layer for optimal performance.

Define Redirect Content Type

Create a Block content type named "Redirect" with fields for SourceURL (text), DestinationURL (link or text), RedirectType (choice: 301/302), Status (choice: active/inactive), and optional Environment (choice: sandbox/production).

Organize Redirects in Content Tree

Create a dedicated folder in the content tree (e.g., /Settings/Redirects/) to store all redirect entries for easy management and bulk operations.

Implement Frontend Redirect Logic

Fetch all active redirects via GraphQL and implement matching logic in your Next.js middleware or edge functions. For Vercel deployments, leverage Vercel's native redirect configuration.

Build Management Dashboard (Optional)

Create a custom frontend dashboard for bulk redirect management, CSV imports, and redirect testing. This can be a separate Next.js page with REST API integration.

ℹ️
Vercel Native Integration
Vercel provides built-in redirect management through its dashboard and vercel.json configuration. You can leverage this by automatically syncing CMS redirects to Vercel's configuration or handling redirects entirely through Vercel's UI for simpler deployments.

💡Additional Considerations

  • Bulk Import: Implement a CSV import feature for migrating large numbers of redirects. This can be built as a separate admin tool using the Optimizely REST API to create redirect content items programmatically.
  • Redirect Chaining: Implement validation to prevent redirect chains (A→B→C) which negatively impact SEO and performance. Check that destination URLs don't themselves have redirects.
  • Wildcard Redirects: Consider supporting pattern-based redirects for common scenarios (e.g., /blog/* → /insights/*). This would require custom matching logic in your middleware.
  • Testing & Validation: Build a redirect testing tool that allows authors to verify redirects work as expected before publishing. Include validation for circular redirects and broken destination URLs.
  • Analytics Integration: Track redirect usage to identify which redirects are frequently accessed and which may be outdated. This can inform redirect retirement strategies.
  • Performance: With large redirect tables (1000+ entries), consider implementing a caching strategy or using a CDN edge function for redirect lookup to avoid bottlenecks.

Geography & Location Search

Enable users to find their nearest mortgage lending officer (MLO) based on zip code. Each MLO record includes latitude/longitude coordinates, and the system uses Google Maps API to convert zip codes to geo coordinates for proximity calculation.

Sample Approach

⚠️
Optimizely SaaS CMS Limitation
There is currently no native geo-search capability in Optimizely Graph. Any future support would be subject to Optimizely's product roadmap and should not be assumed for solution planning.

The implementation approach for location-based search depends on your specific architecture and requirements. Two common patterns include:

Option 1: CMS-Driven with Client-Side Search

Store MLO location data in Optimizely CMS with fields for Name, Title, Contact Information, Address, City, State, Zip, Latitude, and Longitude. Retrieve all locations via GraphQL and perform proximity calculations client-side using libraries like geolib. This approach works well for datasets of approximately 400 locations.

Option 2: Third-Party Integration

Integrate directly with a third-party application or service that houses MLO data. The frontend application calls the third-party API to retrieve location data and perform geo-search operations. This approach may be preferred if MLO data is already managed in an external system or requires real-time updates from non-CMS sources.

Implementation Considerations

Regardless of approach, implement zip code geocoding via Google Maps Geocoding API or similar service to convert user input to coordinates. Use established NPM packages like geolib for distance calculations rather than implementing custom formulas. Consider caching geocoded zip codes to minimize API costs and improve performance.

Next.js Implementation: The implementation varies based on your chosen approach. For Option 1 (CMS-driven), create a location search component that fetches MLO data and uses the geolib NPM package for distance calculations. 💡
External Search Platform Option
For larger datasets (1000+ locations), complex geo-search requirements, or when real-time search performance is critical, consider using a dedicated search platform like Algolia, Elasticsearch, or Azure Search that provides native geo-search capabilities with built-in distance filtering, radius search, and geo-bounding box queries.

💡Additional Considerations

  • Data Authority: Determine where MLO data is authoritatively managed and updated. If data lives in an external system, direct integration may be simpler than syncing to the CMS.
  • Update Frequency: Consider how often MLO data changes. Real-time data requirements favor third-party integration, while relatively static data may be suitable for CMS storage.
  • Data Volume: Client-side approaches work well for datasets up to ~500-1000 locations. Larger datasets should use server-side or external search platforms with native geo-search capabilities (Algolia, Elasticsearch, Azure Search).
  • Geocoding Costs: Google Maps Geocoding API has usage limits and costs. Implement caching of geocoded zip codes to minimize API calls.
  • Search Radius: Allow users to specify search radius (e.g., within 10, 25, 50 miles) to refine results and improve user experience.
  • Additional Discovery: Further requirements gathering should clarify data source, update patterns, expected search volume, and any additional filtering requirements (languages, specialties, availability).
Use Case 05

Footnote Management & Presentation

Implement a system for managing legal disclosures and footnotes across page components. Footnotes can originate from multiple CMS locations, need to be automatically numbered in the order they appear, and aggregated at the page level for display.

Sample Approach

SOLUTION DETAILS

Implement a page-level aggregation system where individual components emit footnote references during rendering, and the page collects, deduplicates, and numbers them before final output. Footnote references may originate from multiple component types or rich text fields and should be normalised during rendering.

Create Footnote Content Type

Define a Footnote block content type with fields for FootnoteID (text), FootnoteText (rich text), and Category (choice field for organization). Store footnotes in a shared location in the content tree or at the page level.

Add Footnote References to Components

In components that require disclosures (Hero, Cards, Product Info blocks), add a ContentArea field for Footnote references. Authors can add one or more footnote blocks to each component.

Implement Page-Level Collection

On the frontend, when rendering a page, collect all footnote references from all components. Deduplicate by FootnoteID to avoid repeating the same disclosure multiple times.

Generate Numbered Footnotes

Assign sequential numbers based on the order footnotes appear on the page. Each component displays superscript numbers (e.g., ¹, ²) that link to the corresponding footnote at the bottom of the page using anchor tags (#footnote-1, #footnote-2).

Render Footnotes Section

At the bottom of the page, render all collected footnotes in numbered order with the full disclosure text.

Next.js Implementation: Create a FootnoteManager utility class that collects footnotes as components render. Each component adds its footnotes to the manager with their position in the page. The manager deduplicates by FootnoteID and assigns sequential numbers. Components render superscript links like <sup><a href="#footnote-1">1</a></sup>. At the page level, render a Footnotes section with <div id="footnote-1"><sup>1</sup> Footnote text here...</div> for each footnote. This enables users to click footnote numbers to jump to the disclosure and back.

✓
Best Practice: Shared Footnotes
Store commonly used footnotes in a shared content tree location (e.g., /Global/Disclosures/) so they can be reused across multiple pages and components. This ensures consistency and makes updating legal language easier.

💡Additional Considerations

  • Automatic vs. Manual Numbering: The recommended approach uses automatic numbering based on appearance order. However, if authors prefer manual control, you could add a DisplayOrder or Number field to the Footnote content type.
  • Deduplication Logic: When the same footnote appears in multiple components on a page, ensure the numbering reflects the first occurrence and subsequent occurrences reference the same number.
  • Print Optimization: Ensure footnotes render properly in print views. Consider adding CSS to keep footnotes with their referenced content when pages break.
  • Accessibility: Implement proper ARIA labels and semantic HTML for footnote links to ensure screen reader compatibility. Use <sup> for superscripts and proper role attributes.
  • Mobile Experience: On mobile devices, consider using tooltips or modals instead of anchor links to avoid excessive scrolling to footnotes and back.
  • Version Control: When footnote content changes, ensure that pages referencing the old version maintain historical accuracy. Consider implementing versioning or archiving for compliance purposes.

Rate Display System

Enable authors to display product rate information throughout the site using structured content relationships. Authors select products via content reference fields, and the frontend dynamically renders current rates with appropriate formatting, links, and disclaimers based on product metadata.

Sample Approach

SOLUTION DETAILS

Implement rate display using structured content relationships where authors select products/rates via content reference fields. The CMS stores product metadata and rate information as structured content types. All rate formatting, link generation, and display logic occurs in the frontend rendering layer, keeping authoring workflows clean and maintainable.

Define Product and Rate Content Types

Create structured content types for Products with fields for ProductID, ProductName, ProductType, and current rate information (RateValue, RateType, EffectiveDate). Products can be managed centrally and referenced throughout the site.

Enable Product References in Content

Add Content Reference fields to page types and components where rate information should be displayed. Authors select products from a picker interface rather than typing codes or shortcuts.

Query Relationships via GraphQL

Fetch page content along with all referenced product data through GraphQL queries. The product relationships are resolved automatically, providing complete rate information to the frontend.

Render Rates on Frontend

The Next.js application processes product data and generates appropriate displays (formatted rates, links, disclaimers) based on product metadata. Any special formatting, APR/APY labeling, or link construction happens entirely in the rendering layer.

Next.js Implementation: When rendering the page, the Next.js application receives complete product data through GraphQL. Components can then format and display rates according to business rules (e.g., "3.50% APY" with appropriate styling, disclaimers, and links to product detail pages). 💡Additional Considerations

  • Rate Freshness: Financial rates often change daily or weekly. Determine whether rates should be updated in the CMS or pulled from an external rate service at runtime. For CMS-managed rates, implement appropriate caching strategies and consider using incremental static regeneration (ISR) in Next.js.
  • External Rate Sources: If rates are sourced from an external system or API, consider whether the CMS should store static snapshots of rates or if the frontend should fetch current rates at render time from the authoritative source.
  • Product Catalog Management: Establish clear ownership of product data. Products referenced across multiple pages should be managed centrally to ensure consistency when rates or product details change.
  • Display Consistency: Implement reusable React components for rate display to ensure consistent formatting, styling, and disclaimer inclusion across all product references.
  • Analytics: Add data attributes to product displays for analytics tracking. This enables measurement of which products generate the most interest and conversions.
  • Compliance: Financial rate displays often have regulatory requirements. Ensure your rendering logic includes all required disclosures, effective dates, and follows legal guidelines for APR/APY display.
  • Authoring Experience: The content picker interface should allow authors to search and filter products by type, status, or other attributes to simplify product selection in content.
Use Case 07

Custom CMS Commands

Enable custom functionality within the CMS, such as a button to "push this page content to a Regions API" for integration with external systems.

Current Limitation & Workaround

NOT CURRENTLY SUPPORTED WORKAROUND AVAILABLE
⚠️
Optimizely SaaS CMS Limitation
Custom CMS UI extensions are not currently supported. Alternative approaches include external dashboards, API-driven workflows, and webhook-based integrations.

While native CMS UI customization is not available, there are several workaround approaches that can achieve similar functionality:

External Admin Dashboard

Build a custom Next.js admin dashboard outside the CMS that allows authorized users to select content and trigger actions (e.g., push to external API, generate reports, sync data). This dashboard can use Optimizely's REST API and GraphQL to read and update content.

Webhook-Based Automation

Configure Optimizely webhooks to trigger external actions when content is published, updated, or reaches a specific workflow state. This enables event-driven integrations without custom UI.

Scheduled Jobs via API

Implement scheduled jobs (using Optimizely's scheduled jobs feature or external cron jobs) that periodically check for content that needs to be synced to external systems based on flags or metadata.

Workflow-Based Triggers

Use Optimizely's approval sequences and workflow capabilities to trigger external actions when content reaches specific approval stages. Combine with webhooks for automation.

💡Additional Considerations

  • Roadmap Monitoring: CMS Extensions are on Optimizely's roadmap. Monitor release notes for updates on when native UI customization becomes available. Once released, you could migrate from the external dashboard to native extensions.
